# pi-supervisor

A pi extension that supervises the coding agent and steers it toward a defined outcome.

## Language

**Supervision**:
The act of observing a coding-agent conversation from outside and injecting steering messages when the agent drifts from the desired outcome.
_Avoid_: monitoring (too passive)

**Outcome**:
The specific, measurable end-state that an active supervision run targets. Set at runtime via `/supervise <outcome>` or the `start_supervision` tool.
_Avoid_: goal (overloaded; Claude Code uses "goal" for its own feature)

**Steering**:
A supervisor-generated user message that redirects the agent back toward the outcome. Delivered as `steer` mid-run or as a deferred plain user message at idle time.
_Avoid_: intervention (used internally for the record, but "steering" is the user-facing concept)

**Sensitivity**:
How aggressively the supervisor checks for drift and intervenes. One of `ultralight`, `low`, `medium`, `high`, or `custom`.
_Avoid_: level (ambiguous — could mean severity of drift rather than aggressiveness of checking)

**Completion checklist**:
The set of required completion checks the supervisor enforces before declaring an outcome achieved.
_Avoid_: criteria (too vague)

**Bootstrap checklist item**:
A checklist item dynamically generated by the supervisor LLM from the desired outcome, focused on externally visible contract verification (e.g., exact CLI behaviour, schema shape, invalid-case handling).
_Avoid_: generated item (too generic)

**Predefined check**:
A built-in, outcome-agnostic checklist item covering process hygiene — such as documentation sync, self-review, or code-smell cleanup — that the user can optionally enable via settings.
_Avoid_: template (implies user-defined); static item (implies it's always present)

**Checklist gate**:
The phase at `agent_end` where the supervisor pauses after its own "done" verdict to run each pending checklist item through a review pass before finally stopping supervision.
_Avoid_: checkpoint (already used for tree labels)

## Checklist items

The completion checklist can contain two kinds of items, distinguished by origin:

1. **Bootstrap items** — generated per-outcome by the supervisor LLM at the start of a run. These are contract-oriented and specific to the task at hand.
2. **Predefined checks** — built-in process-hygiene items (e.g., docs-sync) that the user opts into via settings. These are merged after bootstrap items in the checklist order.

Both kinds share the same `CompletionChecklistItem` shape, but only predefined checks have a stable, hardcoded definition.
